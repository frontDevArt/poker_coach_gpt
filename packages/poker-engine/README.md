# poker-engine

Вычислительное ядро покерного коуча. Единственный источник чисел для скиллов
из `.claude/skills/` и для Nuxt-приложения.

## Установка

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.lock
.venv/Scripts/python.exe -m pip install -e ".[dev]" --no-deps
```

`requirements-dev.lock` пинит версии зависимостей разработки; `--no-deps` во второй
команде не даёт pip разъехаться с этими пинами.

Чтение скриншотов лобби (`lobby read`) — необязательная группа `[lobby]`: RapidOCR, onnxruntime и
Pillow. Ядро и его тесты без неё не меняются; тесты распознавания на настоящих скриншотах без неё
пропускаются.

```bash
.venv/Scripts/python.exe -m pip install -r requirements-lobby.lock
.venv/Scripts/python.exe -m pip install -e ".[dev,lobby]" --no-deps
```

`onnxruntime` зафиксирован на 1.20.1: 1.31.1 на машине пользователя (i5-4460, Windows 10) падает
при импорте (segfault).

Силу руки оценивает `phevaluator` (C-расширение без рантайм-зависимостей; `pokerkit`
остаётся эталоном в тестах). У `phevaluator 0.6.0` есть колёса для Windows на Python 3.13 и
3.14 и исходный архив, так что `.venv` годится от любого Python 3.11+. Прежний оценщик
`eval7` не ставился на Windows с Python 3.13+ и заменён.

## Использование

```bash
.venv/Scripts/poker-engine.exe icm --stacks 75,25 --payouts 70,30
```

Все команды печатают одну строку JSON. При ошибке — `{"error": "..."}` и код возврата 1.
Полный список команд — в `.claude/skills/poker-math/SKILL.md`.

### Команды

| Команда | Для кого | Заметки |
|---|---|---|
| `analyze` | приложение | Разбор состояния со скриншота: ICM, пот-оддсы, PKO |
| `advise` | приложение, скилл `poker-preflop-mtt` | Совет на последнем узле раздачи: действие с размером и почему |
| `coach` | скилл `poker-review-method` | Разбор раздачи по кадрам в файле раздачи: `start`, `step`, `undo`, `lint` |
| `lobby` | скиллы `poker-hand-vision`, `poker-review-method` | Файл турнира из скриншотов лобби: `read`, `find`; `read` — группа `[lobby]` |
| `icm`, `risk-premium` | скиллы, отладка | ICM-эквити, risk premium и bubble factor. Считают только переданные стеки, без поля: верны, когда `--stacks` — весь оставшийся турнир (финальный стол). В середине турнира числа ICM брать из `analyze` (модель «стол + поле») |
| `potodds`, `bounty-ev` | скиллы, отладка | Порог эквити, с головой PKO и без |
| `equity` | скиллы, отладка | Либо `--hands`, либо `--hero` вместе с `--vs-range` |

`equity` работает в одной из двух форм и не смешивает их: `--hands AhKh,AdKd` считает
эквити двух конкретных рук друг против друга, `--hero JhTh --vs-range TT+` — руки героя
против диапазона соперника. `--hands` вместе с `--vs-range` отвергается.

`bounty-ev --bounty` — число, показанное над игроком на экране; оно и есть наличные за нокаут.
Пополам его не делить: половиной полного баунти оно уже является (внёс $3.00 — показано
$1.50), а собственный ценник выбившего растёт на половину взятого. Флаг `--split` убран
намеренно: правильного значения у доли нет, она следует из того, что показано на экране, и
`bounty-ev … --split 0.5` теперь отвечает ошибкой `unrecognized arguments`.

### `analyze` — сквозной разбор состояния со скриншота

```bash
.venv/Scripts/poker-engine.exe analyze --input hand.json
cat hand.json | .venv/Scripts/poker-engine.exe analyze --input -
```

Вход — JSON с ключами `context` (турнирный контекст) и `nodes` (список узлов решения,
по одному на скриншот; разбирается последний, остальные нужны валидатору как история).
Ответ содержит только то, что посчитано: ключи, которых посчитать нельзя, отсутствуют,
а не заполняются нулями. Список `flags` — часть ответа, а не сноска: он перечисляет всё,
что расчётом не является (`mh_bias`, `field_homogeneous`, `ladder_incomplete`,
`late_reg_open`, `payouts_provisional`, `field_from_table`, `no_pushfold`, `vpip_default`,
`icm_pressure_undefined`, `pko`, `bubble_protection`).

ICM в `analyze` считается моделью «стол поимённо + однородное поле» (`icm_field`): места за
столом различимы, остальные `nodes[-1].playersLeft − мест за столом` игроков поля неразличимы
и держат средний стек турнира за вычетом стола. Место героя — настоящее место в турнире, и
приз берётся из лесенки по нему целиком, без обрезания. Стоимость — `2^t × (F+1)` состояний:
экспонента только от стола (не больше десяти мест), поле входит линейно. `icm.heroEquity`
сопровождается `icm.playersLeft` и `icm.tableSeats`.

`field_homogeneous` ставится, когда поле вне стола есть: разброс стеков поля модель не видит.
На финальном столе поля нет, и пометки тоже.

`ladder_incomplete` означает, что интервалы выплат покрывают меньше мест, чем `placesPaid`:
призы за непокрытые места модель считает нулевыми. Это либо недоснятый скриншот лобби, либо
кривое распознавание. Пометка — про вход, а не про число: `icm.heroEquity` занижено, только
если среди непокрытых есть места не глубже `nodes[-1].playersLeft`; места глубже уже вручены
выбывшим и в расчёт не входят. Пока открыта поздняя регистрация
(`late_reg_open`), поле ещё растёт; лесенка при этом предварительна, только если выплаты
сняты до закрытия регистрации (`payouts_provisional`, контекст `payoutsFinal: false`).

Поле `averageStackBb` необязательно: средний стек нужен только, чтобы населить поле вне стола.
Когда игроков в узле столько же, сколько мест за столом, поля нет, и средний стек можно не
присылать; в остальных случаях его отсутствие — отказ с текстом про средний стек.

**PKO** узнаётся по ценникам голов, а не по настройке: `seats[].bountyUsd` — число, показанное
над игроком на экране (наличные выбившему). Есть хоть один ценник — пометка `pko`; тогда ценник
обязателен у героя и у каждого, кто в раздаче, иначе отказ. При определённом сопернике ответ
получает блок `bounty`: `villainPriceUsd`, `knockoutCashUsd` (равен ценнику соперника),
`ownPriceGrowthUsd` (половина взятого), `heroPriceAtRiskUsd`, `bbValueUsd` — доллары за большой
блайнд (призы мест `1..playersLeft`, делённые на фишки стола и поля) — и при колле
`requiredEquityWithBounty`. Голова снижает порог, только если колл накрывает остаток соперника и
герой может его выбить; иначе порог равен `requiredEquity`. Блок `bounty` лежит отдельно от
`icm` и с ним не складывается. Уже взятые баунти в расчёт не входят. Колл против олл-ина до
блока не доходит — см. ограничение ниже.

**Защита на баббле** («ранняя пташка» GG): `context.bubbleRefundUsd` — бай-ин, который рум вернёт
вылетевшему на баббле. ICM учитывает его как приз за места `placesPaid + 1 .. playersLeft`: возврат
получает каждый, кто вылетел вне денег, пока живых больше, чем оплачиваемых мест, открыта ли
регистрация — не важно: `lateRegOpen` на поправку не влияет (так условие прочитано и
подтверждено пользователем; кто из живых ранняя пташка, движок не знает). Применён —
пометка `bubble_protection` и блок `bubbleProtection`: `refundUsd`, `places` (`from`/`to`) и
`riskPremiumWithoutRefund` — риск-премия и bubble factor без возврата, рядом с основными. Когда все
живые уже в деньгах или возврат нулевой, поправки нет, и ответ тот же, что без поля.
`ladder_incomplete` и `bbValueUsd` считаются по лесенке лобби: возврат платит рум, а не фонд.
С правилами акции ПОКЕРОК эта модель расходится (право — только у зарегистрированных до начала,
число защищённых — по размеру поля) — долг D41.

Известное ограничение: раздача, где соперник уже в олл-ине (стек 0 BB), разбору не поддаётся —
`analyze` отвергает её до расчёта ICM сообщением `стек на месте N должен быть > 0`, где N —
`seatIndex` со скриншота. Как возвращать в ICM фишки, уже вложенные выбывающим, — решение о
модели, и оно пока не принято.

Ключи ответа `analyze` — camelCase (`requiredEquity`, `effectiveStackBb`), в отличие от
snake_case остальных команд (`required_equity`). Это намеренно: форма ответа `analyze` —
контракт с приложением, а ключи старых команд уже отгружены скиллам.

### `advise` — совет на последнем узле раздачи

```bash
.venv/Scripts/poker-engine.exe advise --input hand.json
cat hand.json | .venv/Scripts/poker-engine.exe advise --input -
```

Вход — тот же конверт, что у `analyze` (`context`, `nodes`, те же парсеры и проверки), плюс
необязательный `history` — список прошлых ответов `advise` по этой раздаче, по умолчанию `[]`.
Проверяется только его форма: список объектов.

Ответ даёт первый советник реестра (`advice.ADVISORS`), взявший последний узел. Советников два,
по порядку: `pushfold` (короткий стек) и `preflop` (весь остальной префлоп). Не взял никто —
ответ-отказ, а не ошибка: `{"advisor": null, "notApplicable": [{"advisor": "pushfold",
"reason": "…"}, {"advisor": "preflop", "reason": "…"}]}`. `ValueError`
(ключ `error` в CLI) остаётся для битого входа. Ключи — camelCase, как у `analyze`.

**`pushfold`** берёт префлоп-спот короткого стека двух видов: `first_in` — до героя все
сфолдили, эффективный стек (меньшее из стека героя и наибольшего стека после него, с вложенным)
не выше `PUSHFOLD_MAX_BB = 8` BB; `facing_allin` — перед героем ровно один олл-ин, остальные
сфолдили, порога нет. Остальное — отказ с причиной (рейз не в олл-ин, мультипот, постфлоп, все
сфолдили до `BB`, к коллу ничего и т. д.). Подыгра «пуш или фолд, колл или фолд» решается
дважды, по фишкам и по ICM модели поля (с головами в PKO), fictitious play на таблице эквити
«класс против класса» (`data/allin_matrix.json`). Совет — лучший ответ точной комбинации героя
против равновесия соперников по ICM:

- `action` — `allin` | `fold` в `first_in`, `call` | `fold` в `facing_allin`; активное
  действие — при `ev.icm.marginUsd > 0`;
- `sizeBb` — сколько герой ставит: весь стек с вложенным в `first_in`, в `facing_allin` —
  меньшее из олл-ина и стека героя минус уже вложенное героем; при `fold` ключа нет;
- `ev.icm` (`allinUsd`/`callUsd`, `foldUsd`, `marginUsd`) — совет; `ev.chip` (то же в BB) —
  для объяснения ICM-поправки; `ev.bountyUsd` — часть `marginUsd` от голов, только в PKO;
- `ranges.hero` — доля диапазона героя по ICM и по фишкам (`icmPct`, `chipPct`) и частота класса
  его руки (`handFreqIcm`, `handFreqChip`); `ranges.opponents` — участники подыгры по порядку
  хода (`role`: `shover` у олл-инщика, `caller` у отвечающих) с частотами по классам
  (`classes`, шаг 0.01);
- `nash` — эксплуатируемость и число итераций каждого решения (`icm` в долларах, `chip` в BB).

Пометки `advise`:

| Пометка | Что значит |
|---|---|
| `mh_bias` | ICM — Malmuth-Harville, ставится всегда |
| `field_homogeneous` | поле вне стола есть, разброс его стеков модель не видит |
| `pko` | у кого-то за столом есть ценник головы: в ICM-игре головы — наличные выбившему |
| `bubble_protection` | возврат бай-ина на баббле учтён призом за места вне денег |
| `ladder_incomplete` | лесенка покрывает меньше мест, чем `placesPaid` |
| `late_reg_open` | поздняя регистрация была открыта: поле ещё росло |
| `payouts_provisional` | выплаты сняты до закрытия поздней регистрации: лесенка предварительна |
| `field_from_table` | средний стек поля — средний по столу: раздача во время поздней регистрации |
| `no_overcall` | после первого колла остальные фолдят: оверколлы не моделируются (ставится при двух и больше отвечающих) |
| `fold_as_walk` | фолд открывающего — уход банка к `BB`, хотя кто-то, кроме `BB`, ещё ответил бы (и в `facing_allin`: так моделируется фолд олл-инщика) |
| `close_spot` | EV активного действия и фолда равны с точностью допуска: рука смешанная, разница мала |
| `nash_not_converged` | предел итераций достигнут раньше допуска, диапазоны приблизительны |

Ограничения: открытие рейзом, рестил и 3-бет `pushfold` не советует — это советник `preflop`;
оверколлы не моделируются (`no_overcall`); фолд открывающего — уход банка к `BB`
(`fold_as_walk`). Олл-ин соперника на 0 BB `advise` разбирает, а `analyze` по-прежнему
отвергает (D3). Бюджет — 2 секунды на совет, тесты бюджета на 6-, 8- и 9-max `first_in`
(`tests/test_advice_budget.py`): 6-max с пятью отвечающими — ~0.2 с, 8-max с семью — ~0.5 с,
9-max с восемью — ~0.7 с. До плана 5 8-max стоил ~3 с, 9-max — ~8 с: почти всё время уходило на
ICM на чистом Python. Долг D27 закрыт планом 5: ICM модели поля на `numpy`, все `2m + 2` исходов
подыгры — один вызов `icm_field.table_equities_batch` (замер — журнал
`docs/superpowers/state/2026-10-18-plan5-execution-notes.md`, разделы «Фаза 1» и «Фаза 2»).

### Советник `preflop` — весь префлоп

Берёт узел префлопа, который не взял `pushfold`: стек любой глубины, кроме спотов push/fold.
Линия раздачи восстанавливается по кадрам (`investedBb` и `inHand` каждого узла, поле `blinds` не
читается), и по ней читается спот:

| Спот | Линия до героя | Действия героя |
|---|---|---|
| `open` | все до героя сфолдили, эффективный стек выше `PUSHFOLD_MAX_BB` | `fold`, `limp` (только у `SB`, до 1.0), `raise`, `allin` |
| `vs_open` | одно открытие рейзом не олл-ином, остальные сфолдили | `fold`, `call` (только у `BB`), `raise` (3-бет), `allin` |
| `vs_3bet` | герой открыл, один 3-бет не олл-ином | `fold`, `call`, `raise` (4-бет), `allin` |
| `vs_4bet` | герой сделал 3-бет, открывший — 4-бет не олл-ином | `fold`, `call`, `allin` |
| `vs_allin_after_raise` | герой рейзил, соперник пошёл олл-ин | `fold`, `call` |
| `vs_limp` | один лимпер, остальные сфолдили | `fold` (у `BB` — `check`), `raise` (изоляция), `allin` |
| `vs_iso` | герой `SB` первым в банк залимпил, `BB` изолировал не олл-ином | `fold`, `call`, `allin` |
| `vs_allin_after_limp` | герой `SB` первым в банк залимпил, `BB` пошёл олл-ин | `fold`, `call` |

Стек не выше ставки — колл на все: у такого места `fold` и `allin`. Пошаговый разбор: второй и
третий узел героя на префлопе в одной раздаче — нормальный вход (D26); дерево каждого шага
строится от начала префлопа по фактической линии, поэтому диапазоны шага N выведены из того же
равновесия, что и на шаге N−1. Состояния между вызовами нет: вход без `history` самодостаточен.

Отказы (`preflop_line.py`, `preflop_tree.py`; тексты — пользовательские, пинятся тестами):
не префлоп; герой уже в олл-ине; спот push/fold — отвечает `pushfold` (в том числе олл-ин
перед первым решением героя при любом стеке); в банк до героя вошли двое и больше —
мультипот; линия неоднозначна — нужен кадр предыдущего решения героя; все сфолдили до `BB`;
герой вошёл в банк лимпом не с `SB` первым в банк или коллом; 5-бет не олл-ином; лимпер (в том
числе герой `SB`) ответил на изоляцию рейзом не олл-ином; место уже в олл-ине с блайнда; стек 0
вне раздачи.

**Модель.** Дерево «открывший против вошедшего»: первый вошедший после открытия закрывает
остальных (`no_overcall`), колл открытия — только у закрывающего действие (`no_cold_call`), колл
без олл-ина доигрывается терминалом реализации эквити по SPR (`postflop_realization`; раздел
«Модель колла» ниже), олл-ин — по `data/allin_matrix.json`. Равновесие — CFR+ на `numpy`
(`preflop_solver.py`), дважды: по ICM модели поля (с головами в PKO) — совет, EV и диапазоны;
по фишкам — `evBb`. Совет — лучший ответ точной комбинации героя против равновесия соперников,
с блокерами. Лимпер не равновесен: его диапазон — профиль по бейджу VPIP
(`profiles.range_for_vpip`, без бейджа — `DEFAULT_VPIP = 25`), ответ на изоляцию внутри
диапазона решается равновесием.

#### Модель колла

План 5 доигрывал колл открытия вскрытием без ставок, а первый вошедший забирал все мёртвые
деньги: остальные за ним фолдили, колл был бесплатным. Советы `open` и `vs_open` выходили
систематически шире реальных (D30): в замере плана 5 (6-max, у всех 10 и 20 BB, по фишкам) `HJ`
против открытия `UTG` 2.0 входил в банк с 93–94% рук, `UTG` открывал 63–65% рук, на 6–20 BB —
62–78% (журнал `docs/superpowers/state/2026-10-18-plan5-execution-notes.md`, «Фаза 7» и «Фаза
8»). План 6 заменил это двумя правилами (спека
`docs/superpowers/specs/2026-10-21-preflop-call-model-design.md`, §4–§6):

1. **Колл открытия — только у закрывающего действие** (`BB` в дереве открытия, лимпер в дереве
   изоляции). Незакрывающий против рейза не олл-ином выбирает `fold`, 3-бет или `allin`; против
   олл-ина колл у всех — это колл push/fold плана 4. Герою-незакрывающему — пометка
   `no_cold_call`.
2. **Колл без олл-ина — терминал реализации эквити** (`realization.py`, пометка
   `postflop_realization`): банк `P` пары `(a, b)` достаётся `a` с вероятностью

   ```
   p = σ( s · logit(e) + λ · SPR · d ),   s = 1 + κ · SPR,   SPR = R / P,
   ```

   где `e` — эквити класса `a` против класса `b` по `data/allin_matrix.json`, `R` — меньший из
   остатков стеков пары после колла, `d = +1`, если `a` на флопе ходит последним (порядок флопа
   `SB`, `BB`, `UTG…BTN`), иначе `−1`. Чем больше фишек за банком, тем сильнее ставки
   постфлопа растягивают эквити: сильная рука забирает больше своей доли, слабая меньше. При
   `SPR = 0` терминал совпадает с олл-ином, при `κ = λ = 0` — со вскрытием без ставок плана 5.

**Константы — калибровка, а не расчёт:** `REALIZATION_KAPPA = 0.25`, `REALIZATION_LAMBDA = 0`.
Подбор — `scripts/calibrate_realization.py` (запуск из `packages/poker-engine`, ~4 мин в облаке
на 4 ядрах, ~9 мин на машине пользователя): сетка `κ` 0–0.6 с шагом 0.05, `λ ∈ {0, 0.02, 0.05,
0.08}`, деревья по фишкам на столе эталона, цель — сумма квадратов отклонений семи калибровочных

| Действие | Размер «до» |
|---|---|

| изоляция лимпа | 3.0 BB + 1 BB за лимпера; из `BB` — 4.0 BB |
| 3-бет в позиции / без позиции | 3 × / 4 × открытие |
| 4-бет | 2.2 × 3-бет |
| 5-бет | олл-ин |

Размер выше 40% эффективного стека (`COMMIT_SHARE`) — олл-ин. Эффективный стек не больше
своего, поэтому размер не меньше стека с вложенным (короткий стек) сливается тем же правилом.
На сыгранном узле размер — фактический из кадра, правило не применяется. Размер, названный
советником, — всегда размер одного из действий дерева, и у этого действия есть EV.

Ответ (ключи camelCase):

- `action` — действие с наибольшим `evUsd`, равенство — к пассивному; `sizeBb` — его `toBb`, у
  `fold` и `check` ключа нет; `spot`, `heroHand`, `effectiveStackBb`;
- `line` — восстановленная линия до решения героя, с прошлыми действиями героя и фолдами
  (у фолда нет `toBb`);
- `actions` — все действия героя на узле: `toBb` (кроме `fold`/`check`), `evUsd` и `evBb` — EV
  от решения героя до конца раздачи, стеком после раздачи; фолд (у `BB` против лимпа — чек) —
  опорная точка разницы;
- `bountyUsd` — сколько из разницы лучшего действия с опорным (фолдом, у `BB` против лимпа —
  чеком) дают головы, только в PKO;
- `ranges.hero.byAction` — равновесная стратегия героя на узле по классам (нулевые опущены, шаг
  0.01); `handFreq` — частоты класса его руки; `reach` и `reachPct` — диапазон, который герой
  представляет своей линией до узла (частоты классов с тем же шагом и доля из 1326); диапазоны
  на флоп — итог префлопа в файле раздачи (`coach`, ниже);
- `ranges.opponents[]` — участники дерева в раздаче, кроме героя: `role` (`opener`, `3bettor`,
  `4bettor`, `limper`, `shover`, `responder` — ещё не ходил), `reach` — частота класса, с которой
  равновесный соперник сыграл линию, `reachPct`, `stackBb`;
- `nash` — эксплуатируемость и итерации каждого решения (`icm` в долларах, `chip` в BB).

### `coach` — разбор раздачи по кадрам

```bash
.venv/Scripts/poker-engine.exe coach start --hand hand.json --context context.json
.venv/Scripts/poker-engine.exe coach step  --hand hand.json --frame frame.json   # '-' — stdin
.venv/Scripts/poker-engine.exe coach undo  --hand hand.json
.venv/Scripts/poker-engine.exe coach lint  --hand hand.json --text answer.md
```

Одна раздача — один **файл раздачи**, единственное состояние разбора (спека тренера §5):
модель-тренер ничего не помнит и не считает, каждый шаг перечитывает файл.

```json
{
  "format": "poker-coach-hand",
  "version": 1,
  "context": {"...": "форма analyze"},
  "frames": [{"...": "кадры как пришли"}],
  "steps": [{"frame": 1, "advisor": "preflop", "answer": {"...": "ответ advise"}, "why": ["..."]}],
  "streets": {"preflop": {"...": "итог улицы"}}
}
```

- `start` создаёт файл и сразу проверяет контекст; файл уже есть — отказ, перезаписи нет.
- `step` дописывает кадр, выводит узлы из всех кадров заново, зовёт `advise` с ответами прошлых
  шагов в `history`, печатает факты и итог закрытой улицы. Вывод — `{"step", "advisor",
  "answer", "why", "streets"}`. Отказ советников (`advisor: null`) — нормальный шаг, он
  хранится.
- `undo` снимает последний кадр, его шаг и итог улицы, которую закрывал только он: файл после
  `step` + `undo` байт в байт равен файлу до `step`.
- `lint` — линтер чисел текста ответа (ниже); файл не меняется.

Файл пишется целиком: временный файл рядом и `os.replace`. Неудачный шаг файл не трогает.
Ошибки — `{"error": …}` и код 1: «файл раздачи уже есть», «файла раздачи нет», «в раздаче нет
кадров: отменять нечего», «файл раздачи повреждён: <поле>» (`format`, `version`, `context`,
`frames`, `steps`, `streets`, «не JSON»).

**Кадр** (`frames.py`, спека тренера §6.1) — узел `analyze`, переписанный с экрана, плюс:

- `unit`: `"bb"` (по умолчанию) или `"chips"`. В фишках поля — `stackChips`, `investedChips`,
  `potChips`, `toCallChips`, `raiseToChips`, обязателен `blinds.bb > 0`; движок делит на него без
  округления. Поле другой единицы в кадре — отказ («поле stackBb не для кадра в chips»).
- Банк — полный (`potBb` / `potChips`) или только середина (`potCenterBb` / `potCenterChips`):
  тогда движок прибавляет вложенное улицы. Оба — отказ («в кадре два банка»). Что показывает
  клиент GG, проверяется на приёмке; до того это параметр кадра.
- Контекст: `averageStackChips` вместо `averageStackBb` — делится на `blinds.bb` последнего
  кадра.
- Контекст без среднего стека, но со `startingStackChips` (так пишет файл турнира `lobby read`)
  — средний стек на каждом шаге выводит движок (`frames.context_payload`, спека лобби §6).
  Поздняя регистрация закрыта — `startingStackChips × entrants / playersLeft / blinds.bb`
  последнего кадра (`playersLeft` — с кадра, входы — окончательные, из лобби; источник
  `averageStackSource: "lobby"`). Открыта — входы на момент раздачи неизвестны, а окончательные
  завышают средний стек, поэтому он — среднее `stackBb + investedBb` мест первого кадра раздачи
  (`averageStackSource: "table"`, пометка `field_from_table`). **Допущение — без ад-донов и
  ребаев с фишками:** у Fifty Stack их нет; пересмотреть, когда будет лобби турнира с ад-доном.
- `payoutsFinal: false` в контексте — выплаты сняты до закрытия регистрации, пометка
  `payouts_provisional`.
- `coach start --late-reg open|closed` перекрывает `lateRegOpen` контекста: открыта ли была
  регистрация в этой раздаче, решает панель стола её первого кадра («Поздняя регистрация» или
  «Ср. стек»), а не момент съёмки лобби.

**Новые проверки раздачи** (`handstate.validate_hand`, действуют и на `analyze`/`advise`):
стек места не растёт внутри раздачи (допуск — шаг печати `ROUNDING_STEP_BB = 0.1`; «стек на
месте 5 вырос внутри раздачи: было 38.0 BB, стало 39.0 BB»), мест за столом не больше
`seatsPerTable` контекста («мест за столом (7) больше, чем seatsPerTable (6)»).

**Факты `why`** (`explain.py`, спека тренера §8) — `{"key", "value", "display"}`: `value` — число
или строка ответа, `display` — готовая печать. Стек и размер — `2.5 BB`; EV в BB — со знаком и
двумя знаками, `+0.35 BB`; доллары — `+$0.14`; доли — проценты с одним знаком, `15.0%`; роль
участника — словом, `3-беттор` (`value` — код `3bettor`: цифра кода стала бы следом линтера). Факты
`preflop`: `action`, разницы лучшего с опорным и со вторым (`vsBase*`, `vsSecond*`, в долларах и
в BB), `chipBestAction`, `bountyUsd`, `heroRange.<действие>`, `heroHandFreq.<действие>`,
`heroReachPct`, `opponent.<позиция>.role/stackBb/reachPct`, `effectiveStackBb`, `line`,
`flag.<пометка>`; `pushfold` — `marginUsd`, `marginBb`, доли героя и соперников; у обоих —
`potBb`, `toCallBb`, `requiredEquity`. Отказ — `reason.<советник>`.

**Итог префлопа** (`streets.preflop`, спека тренера §7.3) ложится в файл на первом кадре
следующей улицы, его факты — `preflop.*` в `why` этого шага: линия префлопа целиком и
диапазоны дошедших до флопа (`reach`, `reachPct`, `seatIndex`, `position`, `role`, `isHero`,
`stackBb`) по ICM-равновесию того же дерева, что на последнем шаге префлопа. Итога нет —
`{"street": "preflop", "reason": …}`: нет кадров префлопа; на флоп пришли трое и больше; линия
вне дерева; линия push/fold.

**Линтер чисел** (`lint.py`, спека тренера §9). След — числа печати фактов всех шагов файла и
номера шагов `1..N`; ответ — `{"ok": true}` или `{"ok": false, "untraced": ["3.5", …]}` (код 0 в
обоих случаях). Число — `\d+([.,]\d+)?`: запятая — точка, знак отбрасывается, сравнение
строкой (`2.0` и `2` — разные). Не числа: всё в обратных кавычках; позиция с цифрой (`UTG1`,
`UTG+1`); `N-бет`, `N-bet`, `N-max` с начала слова; записи рук старшей картой вперёд — пара
(`77`), класс (`A5s`, `98s`, `T9o`, `K9`), комбинация (`AhKd`). Пара рядом с `%`, `BB` или `$`
— число (`77 BB`, `$77`); цифры, приклеенные к слову (`3bet`, `8max`), — числа.

**Состояние раздачи для этапа 6** (спека тренера §7.1). `hand.Hand` — контекст, узлы и
`street_summary(street)`: итог закрытой улицы, ленивый и кешированный. Советник — протокол
`advice.Advisor`: `name`, `applies(hand)` — `None` или причина отказа, `advise(hand, history)`,
`explain(answer)` — факты. Реестры — `advice.ADVISORS` (`pushfold`, `preflop`) и
`advice.STREET_CLOSERS` (`{"preflop": preflop_advisor.close_street}`). Советник постфлопа
встаёт строкой в оба и читает диапазоны префлопа из `hand.street_summary("preflop")`, а не
пересчитывает их; конвейер `coach` при этом не меняется.

Сквозные серии — `tests/data/coach/*.json`, тест `tests/test_coach_series.py`: раздачи кадр за
кадром с аналитическими ожиданиями (советник и спот шага, пометки, итог улицы или причина,
`line_deviates` связью с ответом прошлого шага, кадр в фишках равен кадру в BB, `undo`); ответ,
собранный из печати фактов, проходит линтер, с вписанным числом — нет. Это регресс смысла
конвейера, а не покерных ответов.

### `lobby` — файл турнира из скриншотов лобби

```bash
.venv/Scripts/poker-engine.exe lobby read <кадры…> [--dir DIR]   # один заход
.venv/Scripts/poker-engine.exe lobby find --title "Fifty Stack $5.50" [--dir DIR]
```

`DIR` по умолчанию — `%USERPROFILE%\Documents\poker-coach\tournaments`. Спека —
`docs/superpowers/specs/2026-10-31-lobby-reader-design.md`.

Пользователь снимает лобби **в два захода**, окно развёрнуто (спека лобби §5): до закрытия
поздней регистрации — вкладки «Инфо» и «Призовой фонд», после закрытия — «Призовой фонд» ещё раз.
Каждый заход — один `lobby read`; порядок кадров не важен, что на кадре — разбор узнаёт по
содержимому. Ответ — `{"tournament": путь, "payoutsFinal", "warnings"}`. Заход 1 создаёт файл
`<название> <YYYY-MM-DD>.json` по названию и дате начала из «Инфо»; заход 2 заменяет в нём
выплаты и входы окончательными (без кадра «Инфо» файл ищется по названию). Год начала на кадре не
виден — берётся из даты изменения самого нового кадра.

Конвейер: `lobby_ocr.ocr_image` (RapidOCR по вырезкам шапки и средней колонки; панели с никами не
читаются) → `lobby_read.read_shot` (поля по форме чисел и расположению, не по подписям и не по
пикселям) → `lobby.save` (проверки спеки §7 и запись целиком: временный файл и замена). Около
11–16 с на кадр на i5-4460.

**Проверки — без угадывания.** Отказ называет строку, поле и кадр, файл при отказе не пишется:
дыра в местах («нет мест 46–69: снимите кадр «Призового фонда», где они видны»), строка, прочитанная
на двух кадрах по-разному, поле с низкой уверенностью распознавания, сумма выплат против
«Призового фонда» после закрытия регистрации, шапка сама с собой (уникальные + ре-энтри = входы,
средний стек против стартовый × входы / осталось в пределах 0.5%), заход 2 против захода 1 (то же
название и стартовый стек, входов не меньше), окончательные выплаты не заменяются
предварительными, готовый контекст — `_validate_context`, как у `coach start`. Предупреждения, а
не отказы: сумма выплат во время поздней регистрации расходится с фондом на пару входов (списки
обновляются не одновременно); кадр не «Инфо» и не «Призовой фонд» пропущен.

Файл турнира — контекст `coach start` (`payouts`, `placesPaid`, `entrants`, `playersLeft`,
`lateRegOpen`, `seatsPerTable`, `startingStackChips`, `payoutsFinal`) плюс справка: `title`,
`start`, бай-ин, `pko`, интервал блайндов, уровень закрытия регистрации, `earlyBird`, призовой
фонд. Среднего стека в файле нет: движок выводит его на каждом шаге (раздел `coach` выше).

**Защиту на баббле (Early Bird) команда не пишет**: право на возврат — только у
зарегистрированных до начала, а лобби этого о герое не знает; `bubbleRefundUsd` при нужде
дописывает в файл сам пользователь; модель-тренер (скиллы L6/L7) файл турнира не правит и поле не
угадывает. Модель движка с правилами рума расходится — долг D41. Разброс стеков поля
(вкладка «Игроки») не читается — D11 отложен.

## Что ещё не сделано

Уровень T2 из спеки — сверка с публичными эталонами — есть для HU push/fold по фишкам (чарт
HoldemResources, `tests/data/hu_nash_chart.json`) и для дерева префлопа по фишкам (публичные
чарты MTT, `tests/data/mtt_reference.json`, раздел «Модель колла»); таблицы эквити и
опубликованные примеры ICM — впереди. Постфлоп, мультипот, колд-колл и лимп героя первым в банк не с
`SB` `advise` не советует: на кадре флопа `coach` даёт итог префлопа и отказ советников,
постфлоп — этап 6. Модули `fgs` и `structure` не реализованы. `analyze`
советника не зовёт и по-прежнему ставит на префлопе пометку `no_pushfold`.
