# Дизайн: скриншот-коуч (vision → структура → расчёт → рекомендация)

Дата: 2026-09-10
Статус: утверждён
Основание: план 1 (`2026-09-09-poker-engine-core.md`) закрыт, ядро считает ICM, risk premium,
пот-оддсы, bounty EV и эквити конкретных рук.
Следующий шаг: план имплементации (writing-plans)

## 1. Задача

Пользователь во время турнира делает скриншот стола в момент решения. Приложение читает
скриншот, восстанавливает состояние раздачи, считает числа движком и выдаёт рекомендуемое
действие. Каждая следующая улица — новый скриншот, учитывающий все предыдущие узлы решения.

Это Ф5 (vision) плюс продуктовый срез Ф7 из основной спеки, взятые раньше Ф2 (pushfold)
сознательно: цель — сквозной работающий прототип, а не полная префлоп-математика.

### Границы

В скоупе: распознавание лобби и стола, схема раздачи, валидатор, расчётный конвейер на
существующем ядре, три расширения ядра из раздела 8, локальное Nuxt-приложение.

Вне скоупа: Nash push/fold (Ф2), Future Game Simulation, PKO (турниры пользователя без голов),
авторизация, деплой, сравнение рекомендаций с фактическими решениями пользователя.

## 2. Поправка к основной спеке

Раздел 2 спеки `2026-09-09-poker-skillpack-design.md` утверждает: «Нет HUD и нет текстового
экспорта hand history. VPIP/PFR/AF соперников недоступны».

**Первая половина верна, вторая — нет.** Клиент GG показывает VPIP каждого игрока бейджем у
аватара: процент раздач, в которых игрок добровольно вложил деньги на префлопе коллом или
рейзом (блайнды не считаются, если не было последующего колла или рейза). Это меняет слой L5
с «профилирование только по текущей руке» на «профилирование по наблюдаемой статистике» и
даёт детерминированный источник для диапазона соперника (раздел 8.2).

Текстового экспорта hand history по-прежнему нет — история раздачи восстанавливается только
из последовательности скриншотов.

## 3. Архитектура

Два обращения к AI, вычисления между ними:

```
скриншот стола
      │
      ▼
 [AI #1: vision]  ──►  DecisionNode (JSON по схеме, только факты)
      │
      ▼
 [валидатор, Python]  ──►  ошибка → карточка с подсвеченным полем, расчёт не запускается
      │
      ▼
 [движок: icm / risk-premium / potodds / equity --vs-range]
      │
      ▼
 [AI #2: рассуждение + скиллы L0/L1/L2/L3/L4]  ──►  рекомендация
```

**Почему два вызова, а не один.** Единственный вызов «скриншот + скиллы → ответ» оставляет
движок не у дел: числа приходят из памяти модели, что запрещено контрактом скилла `poker-math`
первой же строкой. Кроме того, при одном вызове неотличимы ошибка чтения стола и ошибка
рассуждения. При двух — первая видна в карточке состояния, вторая в тексте ответа.

**Почему не три (отдельный AI-валидатор).** AI, проверяющий AI, повторяет его ошибки.
Проверки из раздела 7 детерминированы и пишутся на Python.

AI #1 работает по жёсткой схеме, без рассуждений. AI #2 получает посчитанные числа и не имеет
права вводить свои.

## 4. Вход

### 4.1 Лобби — один раз за турнир

| Вкладка | Что снимается |
|---|---|
| Инфо | бай-ин и рейк, призовой фонд, стартовый стек, интервал блайндов, граница поздней регистрации, игроков за столом, тип ре-энтри |
| Структура | лесенка блайндов с анте, таблица `Входов → Призовых мест` |
| Призовой фонд | **готовая лесенка выплат в долларах** и число призовых мест |

Шапка лобби, присутствующая на всех трёх: текущий уровень и блайнды, `Осталось игроков X / Y`,
`Уникальные | Ре-энтри`, средний и максимальный стек.

Лесенка выплат берётся из вкладки «Призовой фонд» готовой — проценты из бракетов не
пересчитываются. Таблица `Входов → Мест` остаётся запасным путём, когда лесенка не снята.

Клиент прямо помечает, что при открытой регистрации выплаты предварительны. Это переносится
в `lateRegOpen` и далее в пометку вывода (раздел 9).

### 4.2 Стол — по скриншоту на каждое решение

Шапка: уровень, блайнды, время до следующего уровня, приз за 1-е место, `Мой ранг N / M`.
`M` — размер оставшегося поля, `N` — место героя в нём.

Стол: стеки (клиент показывает их в BB), общий банк, вложения текущей улицы, борд, карты
героя, кнопка дилера, VPIP-бейджи, кнопки действий.

Раздача всегда начинается со скриншота префлопа.

## 5. Схема данных

`TournamentContext` — один на турнир:

```
buyin, rake, prizePool, startingStack
blindLevels   : [{ level, sb, bb, ante, minutes }]
payouts       : [{ from, to, amount }]     // из вкладки «Призовой фонд»
placesPaid    : int
entrants      : int      // всего входов
playersLeft   : int
lateRegOpen   : bool
seatsPerTable : int
```

`DecisionNode` — один на скриншот стола:

```
street        : "preflop" | "flop" | "turn" | "river"
level         : int
blinds        : { sb, bb, ante }
heroRank      : int      playersLeft : int
seats         : [{ seatIndex, name, stackBb, investedBb, inHand, isHero, vpip, vpipHands }]
buttonSeat    : int
heroCards     : ["Jh","Th"]
board         : []
potBb         : float
toCallBb      : float
raiseToBb     : float | null
confidence    : { поле → "high" | "low" }
```

`Hand` = `TournamentContext` + `DecisionNode[]` в порядке улиц. История раздачи — это сам
массив; отдельного механизма памяти нет, весь массив уходит в промпт AI #2.

**Стеки в BB, не в фишках**, потому что клиент показывает их так. Следствие: сохранение фишек
проверяется с допуском на округление до 0.1 BB, а не точным равенством.

## 6. Правила распознавания

1. **Позиции не подписаны и AI их не называет.** Vision возвращает `seatIndex` по часовой
   стрелке и `buttonSeat`. Позиции присваивает код: `positions_for(len(seats))` из
   `types.py` даёт порядок от ранней к поздней, заканчивающийся `BTN, SB, BB`; `BTN` кладётся
   на `buttonSeat`, остальные разворачиваются по кругу. Неочевидные случаи 2 и 6 игроков уже
   зафиксированы в `_POSITION_OVERRIDES`.
2. **Карты на аватаре = игрок в раздаче.** Пустой аватар — игрок сфолдил. Это единственный
   признак `inHand`; выводить его из истории ставок не нужно.
3. **`toCallBb` берётся с кнопок действий**, а не вычисляется из банка: клиент печатает
   `Колл 7.3 BB` и `Рейз до 14.5 BB` прямым текстом. Кнопки `Чек / Фолд`, `Чек`, `Бет N`
   означают `toCallBb = 0`.
4. **VPIP-бейдж** пишется в `seats[].vpip`. Число сыгранных раздач — в `vpipHands`, если
   доступно; иначе `null`.
5. **Стеки и банк не пересчитываются AI.** Что напечатано на экране, то и в JSON. Перевод
   BB ↔ фишки, если понадобится, делает код.
6. **`confidence` обязателен**: поля, прочитанные неуверенно (мелкий шрифт, перекрытие
   фишками, обрезанный кадр), помечаются `low` и подсвечиваются в карточке. Это позволяет
   править одно поле вместо вычитки всех восьми стеков.

## 7. Валидатор

Детерминированный, на Python, до любого расчёта. Отказ → расчёт не запускается, карточка
показывает поле-нарушитель.

| Проверка | Основание |
|---|---|
| нет дублей карт по всем узлам раздачи и борду | физическая невозможность |
| `len(board)` соответствует `street` (0/3/4/5) | определение улиц |
| `buttonSeat` существует среди `seats` | целостность посадки |
| `positions_for(len(seats))` не бросает исключение | 2 ≤ игроков ≤ 9 |
| ровно один `isHero`, у героя `inHand = true` | герой принимает решение |
| все стеки ≥ 0, `potBb` > 0 | физика фишек |
| сумма стеков + банк сохраняется между соседними узлами, допуск 0.1 BB × число мест | `TableSnapshot.validate()` |
| множество `inHand` не растёт от улицы к улице | нельзя вернуться в раздачу |
| `toCallBb = 0` при отсутствии кнопки колла | согласованность с п. 6.3 |
| `heroRank ≤ playersLeft` | определение ранга |

Ошибки движка (`_checks.py`) — тоже часть валидации: по конвенции репозитория их тексты
являются пользовательскими сообщениями, поэтому `engine.ts` не глотает stderr, а пробрасывает
разобранный JSON в карточку.

## 8. Расширения ядра

### 8.1 Свёртка поля для ICM

Malmuth-Harville факториален и не считает 782 игрока. Модель поля: реальные стеки со стола
плюс несколько узлов «средний игрок», представляющих остальное поле, всего 12–15 стеков.
Средний стек берётся из шапки лобби, `playersLeft` — со стола.

Известное смещение M-H (завышает вероятность 2-го места крупному стеку) помечается в выводе,
как того требует раздел 8 основной спеки.

**Единицы.** `icm --stacks` и `risk-premium --stacks` принимают целые числа, а стеки со стола
дробные в BB (`72.2`). ICM инвариантен к общему масштабу стеков, поэтому перед вызовом код
умножает BB на 10 и округляет до целого — точность 0.1 BB, ровно та, что напечатана на экране.
Менять сигнатуру CLI не требуется. Инвариант масштабной инвариантности покрывается тестом.

Отвергнуто: ICM только по столу — вдали от призов восемь игроков выглядят как финалка, числа
врут грубо. Monte-Carlo ICM по всему полю — отдельный модуль и секунды на расчёт, это не
прототип.

### 8.2 `equity --vs-range`

Сейчас `equity` требует обе конкретные руки, а карты соперника неизвестны. Добавляется парсер
диапазонов (`22+`, `ATs+`, `KQo`, перечисления) и Monte-Carlo по случайной руке из диапазона.

Диапазон выбирает **код**, по таблице `VPIP → ширина диапазона`, а не AI. Начальные значения
таблицы — калибровочный параметр, уточняемый по мере накопления наблюдений.

При `vpipHands` ниже порога (или `null`) VPIP считается статистически незначимым, код
откатывается на дефолтный диапазон по позиции и **помечает это в выводе**. Бейдж `0` у
только что подсевшего игрока не означает нит.

Тестируемые инварианты (не запомненные числа):
- диапазоны вложены: больший VPIP → надмножество меньшего;
- доля комбинаций диапазона от 1326 монотонна по VPIP;
- `equity(A vs range) + equity(range vs A) + ties = 1`.

### 8.3 Таблица `VPIP → диапазон`

Отдельный модуль данных, не зашитый в логику. Правится без изменения кода.

## 9. Расчётный конвейер и честность вывода

На каждом узле считается всё, что доступно из состояния:

| Величина | Команда | Условие |
|---|---|---|
| ICM-эквити | `icm` | есть лесенка выплат |
| risk premium, bubble factor | `risk-premium` | есть выплаты и оппонент в раздаче |
| требуемое эквити | `potodds` | `toCallBb > 0` |
| фактическое эквити | `equity --vs-range` | известны карты героя |

Сравнение требуемого и фактического эквити делает код, не AI.

**Три пометки, обязательные в выводе:**

1. `lateRegOpen = true` → «поле не финально, ICM ориентировочный». Клиент сам это пишет на
   вкладке выплат; продукт не имеет права быть точнее источника.
2. Свёрнутое поле и смещение M-H.
3. **Рекомендация действия на префлопе не является расчётом**, пока нет Ф2. Она приходит из
   рассуждения AI по скиллам и помечается явно. Постфлоп сравнение эквити расчётное.

Пометки — часть ответа, не сноска мелким шрифтом. Продукт, который врёт точностью, хуже
продукта, который её не даёт.

## 10. Граница Nuxt ↔ Python

`server/utils/engine.ts` — единственное место, знающее, как исполняется ядро: функция на
команду (`icm`, `riskPremium`, `potOdds`, `equity`), внутри — переключатель по переменной
окружения между локальным `spawn('.venv/Scripts/python', ['-m', 'poker_engine.cli', ...])` и
HTTP-вызовом Python-сервиса. Приложение сейчас работает локально, позже переезжает на Vercel,
где подпроцесс невозможен; остальная кодовая база об этом не знает.

Ключ Anthropic — только на сервере, в `.env`. Vision-вызовы идут из Nitro-роутов, не из
браузера.

## 11. Интерфейс

- Экран турнира: три drag&drop-области под скриншоты лобби, распознанный контекст —
  редактируемой формой. Держится на всю сессию.
- Экран раздачи: область вставки скриншота стола. Поддержка drag&drop, `Ctrl+V` и правого
  клика как вставки.
- После распознавания: рекомендация и рядом редактируемая карточка состояния с подсветкой
  полей `confidence: low`. Правка любого поля пересчитывает ответ.
- Под ответом открывается следующая область вставки с табами: новая улица или повторное
  решение на текущей (соперник переставил). Лента узлов растёт вниз, предыдущие видны.

## 12. Верификация

**Golden-set.** 10–20 скриншотов стола и лобби с размеченными вручную `DecisionNode` /
`TournamentContext`. Проверяется только AI #1 — распознавание, независимо от логики решения.
Fine-tuning не применяется: скриншоты являются тестовыми данными, а не обучающими.

**Валидатор** покрывается тестами на каждое правило раздела 7, на синтетических узлах.

**Расширения ядра** — инвариантами из раздела 8.2, по конвенции репозитория: аналитические
свойства, проверяемые на бумаге, а не числа из памяти модели.

## 13. Открытые вопросы

- Начальные значения таблицы `VPIP → диапазон` и порог значимости по числу раздач требуют
  калибровки на реальных наблюдениях.
- Действия соперников между двумя скриншотами героя не сняты. Восстанавливаются приблизительно
  по приросту банка и убыли стеков. Точность этого восстановления не проверена.
- Лесенка выплат прокручивается (165 мест в примере); в кадр попадают верхние строки.
  Для свёрнутого поля этого достаточно, для полного — нет.
