# Дизайн: скилл-пак покерного коуча (Texas Hold'em MTT, GG Network)

Дата: 2026-09-09
Статус: утверждён
Следующий шаг: план имплементации (writing-plans)

## 1. Задача

Собрать проверяемую базу покерных знаний и вычислительное ядро **до** постройки продукта
(AI-разбор рук). Цель этого документа — не приложение, а фундамент: набор навыков,
разбитых по категориям, каждый из которых можно проверить машинно.

Продукт (Nuxt-приложение для разбора рук) строится только после того, как выполнена
приёмка из раздела 9.

## 2. Домен

| Параметр | Значение |
|---|---|
| Игра | No-Limit Texas Hold'em |
| Формат | MTT (турниры), не кэш |
| Платформа | GG Network (GGPoker / Natural8) |
| Бай-ины | $0.25 – $25 (микролимиты) |
| Типы | Classic (обычные выплаты) и Bounty (PKO) |
| Структуры | от 3 мин/уровень (турбо/гипер) до 12 мин/уровень (regular) |
| Столы | 8-max по умолчанию на GG; также 6-max и финалка/HU |

### Ключевые ограничения платформы

1. **Нет HUD и нет текстового экспорта hand history.** VPIP/PFR/AF соперников
   недоступны. Профилирование возможно только по действиям внутри разбираемой руки
   плюс ручная память игрока о сопернике. Это определяет содержание слоя L5.
2. **Ввод руки — скриншот стола или реплея.** Извлечение состояния — задача слоя L6
   с обязательной валидацией.
3. **GG-специфичные механики** (Bubble Protection, All-in Insurance) изменяют
   стандартную ICM-математику и должны быть учтены явно.

## 5. Карта категорий (9 слоёв)

| # | Слой | Содержание | Тип |
|---|---|---|---|
| L0 | Онтология | Нотация рук, позиции (8-max GG), классификация текстур борда, SPR, эффективный стек, словарь линий (RFI/3bet/cbet/probe/donk/float). Структура турнира: BB-ante, скорость уровня, стадия по среднему стеку в bb | справочник |
| L1 | Математика | Пот-оддсы, эквити, fold equity, EV. ICM (Malmuth-Harville, risk premium, bubble factor). FGS. PKO bounty EV. Комбинаторика, блокеры | ядро + тесты |
| L2 | Префлоп | RFI по позиции × эффективный стек (100/40/25/20/15/12/10/7/5/3 bb). Nash push/fold + ICM-коррекция. 3bet/4bet/5bet. Игра против лимпа. PKO-поправки | таблицы из ядра |
| L3 | Постфлоп | C-bet по текстуре × позиции × SPR. Мультипот. Тёрн/ривер: полярность, сайзинги. Блеф-селект по блокерам. SPR < 2 — постфлопа почти нет | правила |
| L4 | Стадии турнира | Ранняя (ICM ≈ 0) → средняя (ante, стил-война) → баббл (максимальный ICM) → пост-баббл → финалка (плоская vs крутая выплата) → HU | правила |
| L5 | Эксплойт микро GG | Профили без статов: лимпер, станция, нит, маньяк. Ликвиды пула: недоблеф на ривере, овер-фолд на баббле, овер-колл флопа. GG-механики: Bubble Protection, All-in Insurance | правила |
| L6 | Vision → HandState | Онтология UI стола GG. Извлечение в структуру. Валидация: Σ стеков + банк = const, легальность действий, консистентность улиц. Дозапрос недостающего | схема + валидатор |
| L7 | Методология разбора | Декомпозиция руки на decision points. Оценка каждого: EV выбранного против лучшей альтернативы. Цена ошибки в bb / %ROI. Приоритизация ошибок по стоимости. Формат вывода | процесс |
| L8 | Golden-set | Эталонные ситуации с известными ответами. Сверка Nash-таблиц с публичными, ICM — с опубликованными примерами. Регресс-тесты | тесты |

**Зависимости:** L0 → L1 → {L2, L3} → L4 → L5. L6 независим. L7 использует все. L8 проверяет L1 и L2.

## 7. Формат скилла

Каждый `SKILL.md` содержит три обязательные части.

**Контракт** — что запрещено:

```markdown
## Контракт
Число в ответе допустимо ТОЛЬКО из вывода `poker-engine`.
Нет вывода команды — нет числа. Оценки вида «примерно 35%» запрещены.
```

**Команды** — откуда берутся цифры:

```markdown
| Нужно | Команда |
|---|---|
| ICM-эквити стеков | `poker-engine icm --stacks 12,30,8,50 --payouts 40,25,18,17` |
| Risk premium | `poker-engine icm-rp --hero 2 --stacks ... --payouts ...` |
| Bounty EV колла | `poker-engine bounty-ev --hero-stack 14 --villain 9 --bounty 2.5` |
| Push/fold порог | `poker-engine pushfold --pos BTN --stack 11 --players 6 --icm ...` |
```

**Правила** — как трактовать результат. Формулы приводятся для понимания, а не для
ручного счёта.

### Условная загрузка слоёв

Девять скиллов одновременно не помещаются в контекст и топят сигнал. Активация по условию,
по образцу P1–P5 из PokerSkill:

| Условие | Загружаем |
|---|---|
| всегда | L0, L1, L7 |
| улица = preflop | + L2 |
| улица ≥ flop | + L3 |
| стадия ∈ {баббл, финалка} или формат = PKO | + L4 |
| всегда, в кратком виде | L5 (полный — при опознанном профиле соперника) |
| на входе скриншота | L6, затем выгружается |
| только в тестах | L8 |

### Потребление продуктом

Nuxt читает те же `.claude/skills/**/SKILL.md`, собирает system prompt по той же таблице
активации и вызывает тот же `poker-engine` CLI через Nitro-роут. Одна база знаний, два
потребителя — Claude Code и приложение. Расхождение исключено по конструкции.

## 8. Вычислительное ядро

| Модуль | Что считает | Алгоритм | Риск |
|---|---|---|---|
| `equity.py` | Эквити рук и диапазонов, эвалюация | `pokerkit`, Monte-Carlo для диапазонов | низкий |
| `icm.py` | ICM-эквити, risk premium, bubble factor | Malmuth-Harville, рекурсия с мемоизацией | средний: M-H факториален по числу игроков. Для 9-max считаем точно только по оплачиваемым местам, остальное схлопываем |
| `fgs.py` | Future Game Simulation, 1–2 уровня вперёд | симуляция раздач | высокий: дорого по времени. Фаза 2 |
| `bounty.py` | PKO: EV нокаута, эффективный банк, порог колла | 50% баунти выплачивается сразу, 50% уходит в собственную голову — в расчёт EV идёт половина | средний |
| `pushfold.py` | Nash push/fold + ICM-коррекция | итеративный best-response до сходимости | высокий: узкое место проекта. Таблицы кэшируются в `data/` |
| `structure.py` | Стадия турнира, средний стек в bb, темп роста блайндов | таблицы структур GG | блокер: нужны реальные данные |
| `handstate.py` | Схема руки и инварианты | pydantic + валидаторы | низкий |
| `cli.py` | Единая точка входа, JSON наружу | — | низкий |

### Известное ограничение Malmuth-Harville

M-H систематически завышает вероятность занять 2-е место для большого стека. Закладываем
явно: в выводе помечаем как известное смещение, на баббле сверяем с Monte-Carlo ICM,
расхождение более 1% выносим флагом в разбор.

### Пробел, закрываемый пользователем

Реальных блайнд-структур GG нет и выдумывать их нельзя. До получения данных стадии турнира
определяются по эффективному стеку в bb, без привязки к минутам уровня.

## 9. Верификация и приёмка

### Четыре уровня проверки

**T1. Аналитические инварианты** — обязаны выполняться математически:

- Σ ICM-эквити всех игроков = Σ призового фонда
- равные стеки → равные ICM-эквити
- игрок со 100% фишек → ICM-эквити равно первому месту
- эквити(A vs B) + эквити(B vs A) + ties = 1
- Σ стеков + банк = константа на протяжении руки

**T2. Сверка с публичными эталонами:**

- HU push/fold из `pushfold.py` сходится к опубликованным Nash-чартам, допуск ±1 комбо
- эквити рук — против публичных таблиц (Equilab / PokerStove)
- ICM — против опубликованных примеров ICMIZER / HRC

Эталонные значения заносятся из источника в момент реализации, не по памяти модели —
тот же контракт, что действует для скиллов.

**T3. Golden-set** — 30 турнирных ситуаций с разобранным ответом. Источники:
`vendor-ref/poker-hand-review` и публичные разборы. Регресс-тест смысла, не только чисел.

**T4. Cross-check** — тот же кейс прогоняется через чужой ревьюер из `vendor-ref`.
Расхождение — флаг на ручное расследование, а не автоматическое признание чужой правоты.

### Линтер против галлюцинаций

Отдельный тест на выходе разбора: любое число в тексте обязано иметь trace до вызова
`poker-engine`. Число без источника — падение теста. Машинная гарантия того, что скиллы
не сочиняют.

### Критерий «навыков достаточно»

| # | Условие | Метрика |
|---|---|---|
| 1 | T1-инварианты | 100% зелёные, без исключений |
| 2 | T2 Nash | HU push/fold сходится к публичным чартам, допуск ±1 комбо |
| 3 | T2 ICM | отклонение от опубликованных примеров ≤ 0.1% |
| 4 | T3 golden-set | 30/30 кейсов, ноль противоречий между слоями |
| 5 | Линтер | 0 чисел в разборе без trace до вызова движка |
| 6 | Слепой тест | 10 свежих рук вне golden-set, разбор проходит ревью пользователя |

Пункт 6 обязателен. Без арбитража живым игроком первые пять пунктов дают систему,
идеально согласованную сама с собой и при этом бесполезную за столом.

## 11. Блокеры на стороне пользователя

Данные, которые нельзя получить самостоятельно и нельзя выдумывать:

1. **Скриншоты лобби со структурами** — по одному турниру на 3 мин, 5–8 мин, 12 мин
   на уровень, плюс один PKO. Идут в `structure.py`.
2. **10–20 скриншотов стола GG** — разные стадии, разное число игроков, олл-ин, мультипот.
   Обучающий и тестовый набор для L6.
3. **Наблюдения о пуле** — что реально делают соперники на целевых лимитах. Затравка
   для L5; в отсутствие статов это единственный источник.
4. **Уточнение по турнирам** — какие серии играются (Bounty Hunters, Daily, Global),
   8-max или 6-max. Влияет на L2 и L4.

Блокеры не останавливают Ф0–Ф3.

## 12. Риски и фолбэки

| Риск | Фолбэк |
|---|---|
| Nash-генерация не сходится или слишком медленная | Опубликованные Nash-чарты заносятся как данные; собственная генерация остаётся только для ICM- и PKO-коррекций |
| Vision плохо читает UI GG | Гибрид: модель извлекает состояние, пользователь подтверждает ключевые поля (стеки, банк) до разбора |
| Смещение Malmuth-Harville на баббле | Monte-Carlo ICM вторым мнением, расхождение более 1% выносится флагом |
| Скоуп в 9 слоёв велик | L3 (постфлоп) режется до минимума: на 15–25 bb в MTT постфлоп редок. Расширение — после Ф7 |

## 13. Явно вне скоупа

- Кэш-игра, Rush & Cash, Spin & Gold
- Другие покерные дисциплины (Omaha, Short Deck)
- Real-time assistance во время игры — только постфактум-разбор
- Автоматизация игры или взаимодействие с клиентом GG
- Мультиаккаунтинг, обход правил платформы

## 14. Сценарий использования: пошаговый разбор (пользователь, 2026-09-25)

Главный сценарий разбора, подтверждённый пользователем:

1. **Во время раздачи** пользователь на каждом своём решении делает скриншот стола
   *перед* нажатием кнопки и решает сам. Тренер в это время не вызывается — RTA
   запрещён правилами GG (§13).
2. **После раздачи** пользователь отдаёт скриншоты тренеру по одному, по порядку.
3. На каждый скриншот тренер отвечает, как правильно действовать в этой точке: действие
   с размером (например, «рейз 2.2 BB», «фолд», «4-бет до 28 BB») и «почему».
4. **Сверку делает сам пользователь, в голове.** Своё решение он тренеру не сообщает,
   тренер его не извлекает, таблицы «совпало/ошибка» и цены ошибки в отчёте нет.

5. **Разбор копит историю.** Каждый следующий шаг — это текущая ситуация плюс всё, что
   было раньше в раздаче: предыдущие кадры и предыдущие ответы тренера. Пользователь
   перестаёт спрашивать на первом расхождении, поэтому если разбор дошёл до шага N, все
   советы на шагах 1..N−1 совпали с его игрой: **линия героя = линия тренера**. Ответ на
   шаге N обязан учитывать эту линию как свою собственную:
   - какой диапазон рук представляет герой после такой линии (для соперника);
   - как действия соперника по улицам сужают его диапазон;
   - план, заложенный раньше (например, блеф с флопа, продолженный на тёрне), не
     бросается без причины, а пересматривается с объяснением, что изменилось.
   Если кадр всё же показывает действие, расходящееся с прошлым советом, тренер
   разбирает дальше по фактической линии.

**Почему так:** если модель видит решение пользователя, её ответ тянется к нему
(подстраивание, anchoring). Тренер на шаге N видит только скриншоты 1..N — будущих кадров,
где уже видно действие пользователя, у него нет, поэтому ответ честный.

Следствия для слоёв:

- L6 — скриншоты приходят серией одной раздачи; предыдущие кадры — контекст (кто что
  делал), текущий — точка решения.
- L7 — вывод на шаг: правильное действие с размером + короткое объяснение. Сравнение с
  действием пользователя не делается. Разбор раздачи — одна сессия с памятью: прошлые
  ответы тренера входят в контекст следующего шага, ответы согласованы по улицам.
- L2/L3 — совет содержит размер действия (рейз 2.2 BB, 3-бет/4-бет в BB), не только тип.
- Ф7 — пожелание: режим тренажёра — споты вне игры как задачи «что делаешь?».
