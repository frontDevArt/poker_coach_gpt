# Дизайн: MVP префлоп-тренера — серия кадров одной раздачи → пошаговый разбор с историей

Дата: 2026-10-21
Статус: решения автора спеки по поручению пользователя («все открытые вопросы решай сам, сразу,
как будет лучше, а не легче», 2026-10-21). Брейнсторма не было.
Основание: этап 5 дорожной карты `CLAUDE.md`; спека скиллпака §5 (L6, L7), §9, §11, §14; спека
плана 5 §5, §7, §12. Парная спека — `docs/superpowers/specs/2026-10-21-preflop-call-model-design.md`
(модель колла, D30): исполняется первой.
Следующий шаг: план `docs/superpowers/plans/2026-10-21-preflop-trainer.md`, Задачи 6–10.

Решения автора помечены **[решение автора]** и собраны в §15.

## 1. Задача

Сценарий спеки скиллпака §14: во время раздачи пользователь делает скриншот перед каждым своим
решением и решает сам. После раздачи отдаёт кадры тренеру по одному. На каждый кадр тренер
отвечает правильным действием с размером и «почему», учитывая всю раздачу до этой точки и свои
прошлые ответы как собственную линию героя. Своё решение пользователь не сообщает.

Советники планов 4–5 уже отвечают на любой префлоп-узел (после спеки модели колла — без искажения
D30). Чего нет: самого конвейера тренера — как кадры одной раздачи копятся между шагами, как
история прошлых ответов попадает в следующий шаг, как диапазоны, выведенные из линии, живут в
состоянии раздачи и переходят на следующую улицу, как тренер объясняет совет только числами
движка и чем это проверяется машинно. Плюс скиллы L6 (кадр → состояние) и L7 (методика ответа).

## 2. Что пользователь получает

Раздача — одна сессия разбора. На каждый кадр префлопа:

```
Шаг 2. 3-бет до 6.0 BB.

Почему:
- 3-бет лучше колла на +$0.21 и фолда на +$0.35 (по фишкам — +0.41 BB против фолда).
- Ты открылся с `UTG1`: соперник видит у тебя 15.0% рук; его 3-бет — 4.2% рук.
- Против этого диапазона `AQs` …

Допущения: колл тебе не предложен — в модели колл открытия только у закрывающего действие.
```

На кадр флопа и дальше: «постфлоп — этап 6», плюс диапазоны обоих игроков на флоп, выведенные из
линии префлопа. Числа в тексте — только из ответа движка; проверка — линтер §9.

## 3. Цели, не-цели, анти-цели

**Цели**

1. Конвейер: кадр → состояние раздачи → точка решения → советник улицы → ответ → объяснение →
   проверка чисел; конвейер не знает об улицах (требование `CLAUDE.md` к этапу 5).
2. Состояние раздачи живёт в файле раздачи, а не в памяти модели: кадры, ответы, итоги улиц.
3. Интерфейс советника: вход — состояние раздачи и история прошлых ответов; выход — действие,
   размер, объяснение. Префлоп — первая реализация, постфлоп этапа 6 добавляется регистрацией.
4. Диапазоны героя и соперника по линии — в состоянии раздачи, переходят на следующую улицу без
   пересчёта советником следующей улицы.
5. Объяснение — список фактов с готовой печатью чисел; линтер — ни одного числа без следа.
6. Скиллы `poker-hand-vision` (L6) и `poker-review-method` (L7).
7. Арифметики модели нет нигде на пути: перевод фишек в BB, сумма банка — в движке.

**Не-цели**

- Постфлоп-совет (этап 6), мультипот (этап 6), профили соперников (этап 7).
- Nuxt-апп и режим тренажёра «что делаешь?» (этап 9).
- Распознавание картинки движком: кадр читает модель-тренер по скиллу L6, движок проверяет.
- Отчёт «совпало / ошибка» и цена ошибки (спека скиллпака §14: сверку делает пользователь).

**Анти-цели**

- число в ответе тренера, которого нет в фактах шага (или прошлых шагов);
- совет по кадру, не прошедшему валидатор;
- файл раздачи, испорченный неудачным шагом;
- ответ шага N, противоречащий шагам 1..N−1 молча (`line_deviates` — да, тихий пересчёт — нет);
- модель-тренер считает сама: делит фишки на блайнд, складывает банк, округляет EV.

## 4. Конвейер

```
кадр (JSON от модели по скиллу L6)
  → coach step: разбор кадра, перевод единиц, кадр в конец списка
  → validate_hand по всей раздаче (+ новые проверки §6.2)
  → состояние раздачи Hand: контекст, узлы, итоги закрытых улиц (лениво)
  → реестр советников по порядку: первый, кто взял последний узел
  → ответ советника (форма планов 4–5, без изменений) + explain(ответ) → факты
  → запись шага в файл раздачи (атомарно)
модель-тренер: текст по фактам → coach lint → ответ пользователю
```

Улица нигде не ветвит конвейер: смена улицы — свойство состояния (итог прошлой улицы считает её
советник, §7), выбор советника — реестр.

## 5. Файл раздачи и команда `coach`

### 5.1 Файл

**[решение автора]** Одна раздача — один JSON-файл:

```json
{
  "format": "poker-coach-hand",
  "version": 1,
  "context": { "...": "форма analyze" },
  "frames": [ { "...": "кадры как пришли, §6" } ],
  "steps": [
    { "frame": 1, "advisor": "preflop", "answer": { "...": "ответ advise" }, "why": [ "..." ] }
  ],
  "streets": { "preflop": { "...": "итог улицы, §7.3" } }
}
```

Кадры хранятся как пришли (аудит того, что прочитала модель); узлы выводятся из них при каждой
загрузке. Ответ хранится целиком: он — `history` следующих шагов. Запись — во временный файл
рядом и `os.replace`: неудачный шаг файл не трогает.

### 5.2 Команды

```bash
poker-engine coach start --hand hand.json --context context.json
poker-engine coach step  --hand hand.json --frame frame.json      # '-' — stdin
poker-engine coach undo  --hand hand.json
poker-engine coach lint  --hand hand.json --text answer.md
```

- `start` — создаёт файл; файл уже есть — отказ (перезаписи нет). Контекст проверяется сразу.
- `step` — кадр в конец, проверка всей раздачи, совет, факты, итог улицы, запись. Вывод: `{"step":
  N, "advisor": …, "answer": {…}, "why": […], "streets": {…}}`. Отказ советников (`advisor: null`)
  — нормальный шаг, он хранится. Битый кадр — `{"error": "…"}`, код 1, файл прежний.
- `undo` — снимает последний кадр и его шаг; файл после `step` + `undo` байт в байт равен файлу до
  `step`. Нужен, когда пользователь говорит «кадр прочитан неверно».
- `lint` — §9, по фактам всех шагов файла.

Тексты ошибок (формулировки — план): файл уже есть; файла нет; отменять нечего; файл повреждён
(не тот `format`, `version`, форма полей) — с указанием поля.

## 6. Кадр

### 6.1 Единицы

Форма узла — та же, что у `analyze` и `advise`, плюс **[решение автора]**:

- `unit`: `"bb"` (по умолчанию) или `"chips"`. В фишках поля — `stackChips`, `investedChips`,
  `potChips`, `toCallChips`, `raiseToChips` и обязателен `blinds.bb > 0`; движок делит на большой
  блайнд без округления. Поля `*Bb` в кадре в фишках — отказ (смешение единиц), и наоборот.
- Банк — либо полный (`potBb` / `potChips`: середина плюс ставки улицы перед местами), либо только
  середина (`potCenterBb` / `potCenterChips`): тогда движок прибавляет вложенное улицы. Оба сразу —
  отказ. Что именно показывает клиент GG, проверяется на приёмке (§11.2), а до того это параметр
  кадра, а не зашитое допущение.
- Контекст: `averageStackChips` вместо `averageStackBb` допустим; делится на `blinds.bb`
  последнего кадра.

Так модель-тренер переписывает с экрана то, что видит, а арифметику делает движок.

### 6.2 Новые проверки серии

В `handstate.validate_hand` (действуют и на `analyze`/`advise`) **[решение автора]**:

- **стек места не растёт внутри раздачи** (допуск — шаг печати `ROUNDING_STEP_BB`): ловит ошибку
  чтения одного места и называет его; вместе со сходимостью фишек даёт «банк не убывает» (D13);
- **мест за столом не больше `seatsPerTable`** контекста (D13: поле не использовалось).

Тексты — новые, через `_checks` где подходят; тест на каждый — `match=`.

Исключений у проверки стека нет, и это не упущение: стек растёт внутри раздачи только при возврате
неуплаченного излишка ставки, а он бывает, лишь когда все остальные сфолдили или в олл-ине на
меньшее. После этого у героя решений нет, кадра нет (спека скиллпака §14: кадр — перед своим
решением). Побочный банк фишек не возвращает: в нём ставки уравнены.

## 7. Состояние раздачи и итог улицы

### 7.1 `Hand` и интерфейс советника

**[решение автора]** Новый тип `hand.Hand`: `context`, `nodes`, `street_summary(street)` — итог
закрытой улицы, считается лениво и кешируется. Протокол советника:

```python
class Advisor(Protocol):
    name: str
    def applies(self, hand: Hand) -> str | None: ...
    def advise(self, hand: Hand, history: list[dict]) -> dict: ...
    def explain(self, answer: dict) -> list[dict]: ...
```

`advice.ADVISORS` — прежний порядок; `advice.STREET_CLOSERS = {"preflop": preflop_advisor.close_street}`
— реестр итогов улиц. Советник постфлопа этапа 6 добавляет строку в оба реестра и читает
диапазоны из `hand.street_summary("preflop")`. CLI `advise` строит `Hand` из конверта; форма его
ответа не меняется. Смена протокола — `refactor(engine)` с механической правкой вызовов в тестах.

### 7.2 Диапазон героя в ответе

К `ranges.hero` ответа `preflop` добавляются `reach` (частота класса героя по линии до узла, шаг
`CLASS_FREQ_STEP`) и `reachPct` — «какой диапазон рук представляет герой после такой линии» (спека
скиллпака §14). Ключ добавочный, прежние не меняются.

### 7.3 Итог улицы префлопа

Префлоп закрыт, когда в раздаче есть кадр следующей улицы. Итог **[решение автора]**:

- линия префлопа целиком — до последнего действия улицы. Последний кадр префлопа даёт линию до
  решения героя; действия после него (ход героя, ответы) восстанавливаются по первому кадру
  следующей улицы: вложенное префлопа места = стек на старте раздачи минус стек на флопе;
- дерево — то же, что на последнем шаге (тот же корень и стеки), путь продолжен до терминала;
- диапазоны — `reach` каждого участника, дошедшего до флопа, по ICM-равновесию (как совет), шаг
  `CLASS_FREQ_STEP`, и `reachPct`; у каждого — `seatIndex`, `position`, `role`, `isHero`.

Форма: `{"street": "preflop", "line": […], "ranges": [ … ]}` или `{"street": "preflop", "reason":
"…"}`, когда итога нет: кадров префлопа нет; на флоп пришли трое и больше (мультипот); линия
вне дерева (колд-колл незакрывающего, лимп не с `SB`); линия push/fold (олл-ин и колл —
дальнейших решений нет). Тексты — план.

Итог считает советник префлопа (`close_street`) — это его диапазоны. Советник флопа их не
пересчитывает: читает из состояния.

## 8. Объяснение `why`

**[решение автора]** `explain(answer)` советника возвращает список фактов `{"key", "value",
"display"}`: `value` — число или строка из ответа, `display` — готовая печать. Правила печати:
стек и размер — `{:.1f} BB`; EV в BB — со знаком, два знака (`+0.35 BB`); доллары — со знаком, два
знака (`+$0.14`); доли — проценты, один знак (`15.0%`).

Факты `preflop`: действие с размером (`рейз до 2.0 BB`); разница лучшего с опорным и со вторым — в
долларах и в BB; лучшее по фишкам, если оно другое (ICM-поправка); `bountyUsd` в PKO; доля диапазона
героя по каждому действию узла (`byAction`, взвешенно по комбинациям); частота класса героя, если
она смешанная; `reachPct` героя и каждого соперника, их роли, позиции, стеки; эффективный стек,
банк, сумма колла; требуемая эквити колла (`potodds`), если колл есть; линия строкой; пометки.
Факты `pushfold`: действие и размер, `marginUsd` и `marginBb`, `bountyUsd`, `icmPct` и `chipPct`
героя, частоты класса, доли соперников, требуемая эквити колла в `facing_allin`, пометки. Отказ —
факты-причины (тексты отказа).

Итог улицы (§7.3) — тоже факты шага, на котором улица закрылась.

## 9. Линтер чисел

Спека скиллпака §9: «любое число в тексте обязано иметь trace до вызова `poker-engine`».
**[решение автора]** `lint.untraced(text, facts) -> list[str]`:

- **след** — числа из `display` фактов всех шагов файла и номера шагов `1..N`;
- **число в тексте** — `\d+([.,]\d+)?`; запятая читается как точка, знак отбрасывается; сравнение
  — строкой после нормализации: `2.0` и `2` — разные (тренер переписывает печать, не округляет);
- **не числа**: всё в обратных кавычках; имена позиций с цифрой (`UTG1`, `UTG+1`); `N-бет`,
  `N-bet`; `N-max`; записи рук и комбинаций (`77`, `A5s`, `T9o`, `AhKd`) без единицы рядом —
  число со знаком `%`, `BB` или `$` рядом — всегда число;
- ответ `{"ok": true}` или `{"ok": false, "untraced": ["3.5", …]}`.

Скилл L7 требует прогонять линтер до отправки ответа и чинить текст, а не факты.

## 10. Скиллы

**`poker-hand-vision` (L6)** — кадр и контекст со скриншота: таблица полей узла и контекста с тем,
где их искать на экране; правила — читать только видимое, не угадывать скрытое; не считать
(фишки — в `*Chips`, банк — как показан, движок сведёт); нет обязательного поля — один точный
вопрос пользователю; ошибка `coach step` называет поле — перечитать именно его, при сомнении
спросить; подгонять числа под валидатор запрещено. Особенности клиента GG, которые без скриншотов
пользователя неизвестны (что показывает «банк», фишки или BB, бейдж VPIP), — отдельным разделом
«проверить на приёмке» (§11.2).

**`poker-review-method` (L7)** — сессия разбора: `coach start` по лобби; на каждый кадр — L6,
`coach step`, текст по фактам, `coach lint`, ответ. Формат ответа §2. Правила: линия героя = линия
тренера; `line_deviates` — сказать прямо и разбирать по факту; не спрашивать, что сделал
пользователь, и не сравнивать; отказ — пересказать причину, действия не называть; пометки — по
таблице скилла `poker-preflop-mtt`; кадр флопа — «постфлоп — этап 6» и диапазоны итога префлопа;
«кадр прочитан неверно» — `coach undo`. Скиллы `poker-ontology` и `poker-math` ссылаются на него
(D13).

`poker-preflop-mtt` — раздел «серия кадров»: вход через `coach`, а не ручной сбор `nodes` и
`history`.

## 11. Приёмка

### 11.1 Синтетические серии

`tests/data/coach/*.json` — серии кадров одной раздачи (контекст и кадры) с аналитическими
ожиданиями: какой советник на каком шаге, спот, пометки, итог улицы и причина его отсутствия,
`line_deviates` на отклонившемся кадре; ответ, собранный из `display` фактов шаблоном §2, проходит
линтер, тот же ответ с вписанным числом — нет. Это регресс смысла конвейера, а не покерных ответов
(эталонные ответы — golden-set этапа 8).

### 11.2 Слепой тест пользователя

Спека скиллпака §9, пункт 6. **[решение автора]** Последняя фаза плана просит у пользователя 3–5
реальных раздач (серии скриншотов и лобби), прогоняет тренер по скиллам и записывает в журнал:
что прочитано неверно, что непонятно в ответе, вердикт пользователя. Здесь же решаются вопросы
клиента GG §10. Без данных план закрывается со статусом «MVP собран, приёмка ждёт данных
пользователя» — это не блокирует реализацию (`CLAUDE.md`: данные — по ходу).

## 12. Инварианты для тестов

1. Кадр в фишках даёт тот же узел, что кадр в BB с поделёнными значениями; смешение единиц,
   нет `blinds.bb`, оба вида банка — отказы с текстом.
2. `potCenter*` плюс вложенное улицы равен `pot*` того же кадра.
3. Неудачный `step` — файл байт в байт прежний; `step` + `undo` — тоже.
4. `history` шага N — ответы шагов 1..N−1 по порядку; отклонение героя от ответа шага N−1 даёт
   `line_deviates` на шаге N.
5. Новые проверки §6.2 — по тесту с `match=`; фикстуры 8/9-max получают свой `seatsPerTable`.
6. Протокол: у каждого советника реестра есть `explain`; `STREET_CLOSERS` знает префлоп; ответы
   `advise` на фикстурах планов 4–5 те же (кроме добавочных ключей §7.2).
7. Итог префлопа: «открыл, `BB` заколлировал» — `reach` героя пропорционален `byAction.raise` шага 1,
   `reach` `BB` — его частоте колла на узле; мультипот на флопе, нет кадров префлопа, линия вне
   дерева, push/fold — причины с текстом.
8. Факты: каждое `display` — печать своего `value` по правилам §8; ключи фактов на каждом споте.
9. Линтер: след, не след, исключения §9, запятая, знак, `2.0` против `2`, номера шагов.
10. Сквозные серии §11.1.
