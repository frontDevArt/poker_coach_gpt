## 3. Решения, принятые за автора в этой сессии

**Task 6:**

- **R1.** Шесть inline-гардов из сниппета плана заменены вызовами `_checks.py`. План

- **R6.** Имена гардов выбраны по грамматическому роду: `приз за место {n}` вместо `выплата…`,

  диктует `positions_for` всем остальным потребителям.

## 4. Открытые вопросы к автору — их четыре, и два из них тяжёлые

**Тяжёлые. Оба про модель, оба меняют печатаемые числа.**

1. **ICM не масштабируется на реальные лесенки выплат.** Перебор Malmuth-Harville при
   пятнадцати узлах поля переносит максимум шесть оплачиваемых мест. Настоящий турнир платит
   165. Сейчас такой вход честно отвергается, но это значит, что `analyze` не считает ICM для
   того самого случая, ради которого писался. Варианты: быстрее считать (Malmuth-Harville с
   мемоизацией суффиксных произведений, либо приближение Робертса/Тайсена), либо сознательно
   ограничивать глубину выплат и помечать смещение флагом, либо сворачивать поле в меньшее
   число узлов. Все три меняют числа; выбор — за автором, и это предмет отдельного плана.

2. **Соперник в олл-ине (стек 0 BB) разбору не поддаётся.** `validate_hand` ноль пропускает
   (`check_non_negative`), `reduce_field` требует положительного (`check_positive`), и
   канонический ICM-спот отвергается целиком. Как учитывать фишки, уже вложенные выбывающим, —
   решение о модели.

**Лёгкие. Помечены ещё в Task 5, Task 7 их не закрыл.**

3. Нужен ли `average_stack_bb` необязательным: при `players_left == len(table)` он в расчёте
   не участвует, но всё равно валидируется.
4. Остаётся ли нумерация мест 0-based в сообщении `стек на месте {seat}`, если UI показывает
   места с единицы.

**Сознательно отложенные мелочи** (все записаны в ledger, ни одна не блокирует; отдать их
финальному ревью для сортировки):

- `payout_ladder` не отвергает `places <= 0` и при пересекающихся интервалах отдаёт победу
  последней записи.
- `positions_for(...)` в `_validate_node` — выражение-стейтмент ради побочного эффекта.
- `places_paid`, `seats_per_table`, `late_reg_open` разбираются, но не валидируются и не
  используются.
- Гарда «банк не убывает между улицами» нет, и граничный тест допуска этим пользуется.
- `handstate.py` — самый большой модуль пакета; при следующем расширении разделить разбор и
  валидацию.
- `except ValueError` вокруг `risk_premium`/`bubble_factor` шире, чем описывает его комментарий
  (комментарий расширен, перехват — нет).

## 5. Ловушки окружения и уроки процесса

Всё проверено на этой машине, всё стоило времени хотя бы один раз.

- **`types.py` затеняет стандартный модуль.** Не запускать `python` со скриптом, когда рабочий
  каталог — `packages/poker-engine/src/poker_engine`: интерпретатор не стартует вообще.
  Запускать из `packages/poker-engine` или из корня репозитория.
- **`pyproject.toml` уже держит `addopts = "-q"`.** Свой дополнительный `-q` даёт `-qq` и
  глушит итоговую строку `N passed`. Полный прогон гонять **без** своего `-q`.
- **Полный прогон — около 8 минут** (282 теста, 498 с). Запускать синхронно с таймаутом
  600000 мс, не в фоне: фоновый прогон не переживает обрыв сессии.
- **Мутационный прогон обязан быть единственным процессом.** В Task 6 наложение двух
  экземпляров скрипта испортило рабочий файл. Перед стартом убедиться, что фоновых экземпляров
  не осталось; сбрасывать `__pycache__`; запускать `-B -p no:cacheprovider`; откат сверять
  `diff` с эталонной копией.
- **Голый `pytest.raises(ValueError)` в этих модулях не проверяет ничего.** Гарды взаимно
  затеняются: снесёшь один — отказ придёт от следующего по ходу. В каждый тест на отказ —
  различающий `match=`, и пин проверять грепом по соседним сообщениям.
- **Мутировать оператор — не то же, что снести ветку.** Класс «снести гард целиком»
  обязателен. За этот план он вскрыл переживших мутантов трижды, и каждый раз таблица
  исполнителя рапортовала «0 выживших» — потому что описывала придуманные мутации, а не
  перечень точек отказа в коде. Проверять надо код против тестов, а не таблицу.
- **Утверждение вида «это сломает будущие сниппеты» проверять грепом, а не памятью.** В Task 4
  такое утверждение продержало долг лишний круг и оказалось выдуманным.
- **Чинить контракт слоя целиком за один проход.** Дыра в разборе JSON закрывалась в четыре
  приёма только потому, что каждый раз чинили то поле, на котором споткнулись, а не все.
